# AssetTrust v0.39 — Confidential recipient sharing architecture

**Scope:** secure capability-based recipient access to an *existing non-official private evidence PDF*, guarded by two independent administrators. This does not establish legal title, recipient identity, registry status, or government certification.

## Bounded contexts and separation of concerns

- `apps/api/src/contexts/report-sharing/domain/share-policy.ts`: framework-free input policies, 256-bit random token/code generation, separate domain-bound SHA-256 commitments, constant-time credential comparisons and expiry/usage predicates.
- `apps/api/src/contexts/report-sharing/infrastructure/report-sharing.module.ts`: NestJS admin/auth boundaries, database transactions, tenant checks, two-administrator approval, revocation, recipient redemption, current issuance safety gates and detached signing receipt.
- `apps/api/sql/017_report_recipient_shares.sql`: FK tenant isolation, separate tokens stored as commitments only, pending→active/rejected and active→revoked state guard, bounded redemptions, immutable successful-redemption records.
- `apps/web/src/ReportSharingAdmin.tsx`: existing issued-report administration integration. Privileged creation, decision, revoke, usage/audit history and one-time credential display.
- `apps/web/src/ReportRecipientPage.tsx`: anonymous recipient form at `/#receive/report`. The Share ID is not confidential, but neither 256-bit secret is put in a URL. Redemption is via rate-limited `POST /api/v1/reports/recipient/redeem` and returns a PDF+detached Ed25519 receipt.

## Threat model and controls

1. **Tenant confusion:** admin list/create/approve/revoke all require current organization-admin authority, current MFA/step-up, and organization-bound lookup/foreign keys. No platform-wide override.
2. **Self-approval:** the proposing admin cannot approve their own grant. The proposing admin must still be an active org admin at decision time. No recipient gets access while a share is `PENDING`.
3. **Stolen link:** `accessToken` and `accessCode` are independent 256-bit random secrets; only their domain-separated hashes are persisted. The operator must deliver them via separate trusted channels. If *both* are stolen the bearer can redeem: this is capability possession, **not verified personal identity**.
4. **Replay and abuse:** 1–168-hour duration begins on approval; 1–5 successful redemptions maximum; revoke at any time; 5 recipient POST requests per minute under the application throttler. Distributed enforcement depends on reverse proxy and persistent multi-node rate-limit storage.
5. **Race conditions:** share row is locked `FOR UPDATE` on redemption. Issued-report and case rows are locked `FOR UPDATE`, then withdrawal/dispute/supersession flags are queried in a *separate* fresh READ COMMITTED statement. FK references to report/case rows block conflicting writes until this transaction commits. Successful redemption records and count increment are atomic. No file is returned on a failed transaction.
6. **Report changes:** only current, closed, non-withdrawn, non-superseded, dispute-free issued evidence is eligible at proposal, approval, and every redemption. SHA-256 of the originally issued canonical snapshot is rechecked. Withdrawal pending also blocks redemption. No evidence is altered.
7. **Download privacy:** no secrets in routes, query strings, audit details or server storage. Admin actions go to the existing tenant audit chain; recipient successes go to an append-only, no-identity redemption ledger. Invalid guesses are denied generically without creating unbounded database logs.
8. **Cryptographic integrity:** the PDF is generated by the existing v0.37 renderer with the active approved organization layout, and a *detached* Ed25519 receipt signs the exact PDF hash. Recipients must pin an independently trusted issuer public key. This is not PAdES, and an authentic PDF does not imply the statements are true.

## Access state machine

`PENDING` → `ACTIVE` or `REJECTED` (decision by a distinct, currently active MFA-authenticated org admin). `ACTIVE` → `REVOKED` (active org admin, fresh MFA, explicit reason). `ACTIVE` can increase `download_count` by **one** per atomic success, up to `max_downloads`. Time expiry is interpreted as unavailable without modifying history. `REJECTED` and `REVOKED` are terminal. Database transition triggers reject other modifications and DELETE; issued reports remain separate and immutable.

## API contract (JSON)

| Method | Route | Auth | Purpose |
| --- | --- | --- | --- |
| `GET` | `/api/v1/reports/shares` | Current org admin + step-up | Tenant-scoped shares and successful redemption history, no secrets |
| `POST` | `/api/v1/reports/shares` | Current org admin + step-up | Propose share, return credentials *once* |
| `POST` | `/api/v1/reports/shares/:id/decision` | Different org admin + step-up | Approve or reject |
| `POST` | `/api/v1/reports/shares/:id/revoke` | Current org admin + step-up | Revoke active capability, record reason |
| `POST` | `/api/v1/reports/recipient/redeem` | Two bearer credentials; throttled | Atomic private PDF+receipt redemption; no credentials in URL |

### Create request example

```json
{
  "reportId":"a1234567-1234-4234-8234-1234567890ab",
  "recipientLabel":"Authorized legal reviewer",
  "reason":"Limited disclosure to independently review the completed land due diligence",
  "expiresHours":24,
  "maxDownloads":1
}
```

The create response includes `id`, `status`, `accessToken` and `accessCode`. Do not include the secrets in emails sent together, URLs, screenshots, server logs, bug reports, databases, or Git. If lost, reject/revoke and issue a new share rather than attempting recovery.

## Known gaps and release blockers

- No installed dependencies, reproducible `package-lock.json`, full API/web build, authenticated browser test, or live PostgreSQL run in the artifact environment; offline test fakes are not real row locks.
- No independent recipient identity/KYC/email-OTP binding; bearer credentials can be transferred, so restrict particularly sensitive records or add a stronger verified-recipient flow before real customer use.
- Rate limiting is app-instance local unless a shared backend is configured; reverse proxy must enforce HTTPS, logging redaction, response no-store, DDoS controls, alerting and key management.
- No delivery service for credentials or secure integration with email/SMS; operators manually deliver the two secrets via separate channels.
- No externally hosted key registry, key rotation/revocation trust chain, certificate authority, PAdES PDF signing or government registry integration.
- No completed penetration test, load test, disaster recovery drill, legal and data protection review.
- A 'successful redemption' records that the server generated and returned a response; it does not prove the browser saved the file.
